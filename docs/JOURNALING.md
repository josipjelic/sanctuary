# Journaling System

This document describes how the AI-guided journal works in Sanctuary: the question structure, all prompt templates, how `user_state` is built and used, and the privacy rules that apply throughout.

---

## Overview

Each journal session is a guided conversation of up to **5 questions** across two phases:

| Turn | Phase | Type | Description |
|------|-------|------|-------------|
| 0 | Core | Hardcoded | Fixed opening question — always the same |
| 1 | Core | LLM | Sub-question exploring the Q1 answer |
| 2 | Core | LLM | Deeper sub-question within the same thread |
| 3 | Lookback | LLM (optional) | Asks how an unresolved concern from the past 7 days has progressed |
| 4 | Lookback | LLM (optional) | Asks about a second unresolved concern, if one exists |

**Core questions (0-2)** always run. The server may return `{ "done": true }` after Q2 if the AI judges the user has reflected sufficiently.

**Lookback questions (3-4)** are optional. If the user has no completed journal entries from the past 7 days, the session ends after Q2. If the AI finds no unresolved concerns worth asking about, or after two lookback turns, the session ends.

The client never decides when to end the session — it always calls `journal-next-question` after each answer and acts on the server's response (`{ question }` or `{ done: true }`).

---

## Question 1 — Opening (Hardcoded)

Q1 is never AI-generated. It is returned instantly, with no LLM call, no context fetch, and no latency.

```
JOURNAL_OPENING_QUESTION_V1 =
  "Take a moment to settle in. What's on your mind today — something that
   happened, a feeling, or just a thought that's been with you?"
```

**Rationale**: The opening clause ("Take a moment to settle in") invites the user to slow down, consistent with Sanctuary's calm, intentional brand. The three explicit entry points — event, feeling, thought — cover both external and internal dimensions of a day, reducing blank-page anxiety without presupposing content. The constant is versioned (`_V1`) so future revisions are trackable alongside existing sessions.

**Stored as**: `journal_sessions.opening_question_version` records which version was active.

## Questions 2 and 3 — Sub-questions (LLM)

Q2 and Q3 are generated by the `journal-next-question` edge function using OpenRouter. They are explicitly framed as **sub-questions** — they must explore and deepen what the user shared in their Q1 answer, not introduce unrelated new topics.

### System prompt

```
You are a compassionate journaling guide for the Sanctuary app. Your role is to ask
thoughtful follow-up questions that help the user reflect more deeply on what they
shared in their opening answer.

Rules:
- Your questions must be sub-questions of what the user shared in Q1 — explore and
  deepen that thread, do not introduce unrelated new topics
- Q2 (first follow-up) should go to the heart of what the user shared — the feeling,
  the situation, or the tension within it
- Q3 (second follow-up) should go one layer deeper — a why, an unexplored angle, or
  the emotional undercurrent
- NEVER assume anything about the user's life situation (no mentions of "your job",
  "your partner", "your kids", "your work" etc.) UNLESS the user has explicitly
  mentioned these in their answers
- If the user's context mentions unresolved struggles or ongoing challenges, gently
  weave them in only when it feels genuinely natural to the current thread
- Keep questions short, warm, and open-ended (max 20 words)
- If the user has shared enough meaningful reflection across all turns, respond with
  {"done": true} instead of a question
- Return ONLY valid JSON: {"question": "..."} or {"done": true}

[Today's check-in block — if present]
Today's check-in:
- Mood: <mood>
- Intention: <intention>

[OCEAN personality block — if present]
User's personality (OCEAN — use to tune tone and depth, never mention directly):
- Openness: <level> (<score>)
- Conscientiousness: <level> (<score>)
- Extraversion: <level> (<score>)
- Agreeableness: <level> (<score>)
- Neuroticism: <level> (<score>)
Guidance: <hints based on scores>

User's current context (may be empty for new users):
<user_state.content or placeholder>
```

### User message

```
The user has answered <N> question(s) so far. Here is the conversation:

Q1: <opening question>
A1: <user's answer>
[Q2: <follow-up question>
A2: <user's answer>]

This is question <N+1> of a maximum of 3. Generate the next sub-question exploring
what the user shared, or signal done if the user has reflected sufficiently.
```

### Context loaded for Q2/Q3

All three context sources are fetched in parallel from Supabase and are non-fatal — missing data gracefully degrades:

| Source | Table | Used for |
|--------|-------|----------|
| User profile | `user_state.content` | Background context in system prompt |
| Today's check-in | `daily_checkins` (today's row) | Mood and intention block |
| Personality | `ocean_profiles` | Tone tuning via OCEAN block |

## Questions 4 and 5 — Lookback (LLM, Optional)

Q4 and Q5 are generated only when the user has completed journal sessions in the past 7 days. They ask how an unresolved concern or challenge the user mentioned previously has progressed.

### How past entries are fetched

1. Query `journal_sessions` for up to 5 completed sessions within the past 7 days, excluding the current session, ordered by `completed_at DESC`.
2. Query `journal_entries` for all answered entries (`answer IS NOT NULL`) belonging to those sessions.
3. Group by session, ordered by `turn_index ASC` within each session.

If no completed sessions exist from the past 7 days, the function returns `{ "done": true }` immediately without calling the LLM.

### System prompt

```
You are a compassionate journaling guide for the Sanctuary app. The user has just
finished their main reflection for today. Your task is to ask ONE gentle follow-up
question about an unresolved concern or challenge they mentioned in their journal
over the past 7 days.

Rules:
- Review the recent journal entries below and identify an unresolved concern, worry,
  or challenge the user has been carrying
- Ask specifically how that situation has progressed, changed, or been resolved since
  they mentioned it
- Reference the concern naturally and warmly (e.g. "You mentioned feeling anxious
  about X last week — how has that been?")
- If today's session already covered a particular concern (shown in the current
  session Q&A below), pick a different unresolved concern OR respond with
  {"done": true} if nothing else stands out
- If no clear unresolved concerns appear in the recent entries at all, respond with
  {"done": true}
- Keep the question short and open-ended (max 25 words)
- Return ONLY valid JSON: {"question": "..."} or {"done": true}

Recent journal entries (past 7 days):
[Session from YYYY-MM-DD]
Q1: <question>
A1: <answer>
...

---

[Session from YYYY-MM-DD]
...
```

### User message

```
Current session Q&A so far:

Q1: <opening question>
A1: <answer>
Q2: <sub-question>
A2: <answer>
Q3: <sub-question>
A3: <answer>
[Q4: <lookback question>
A4: <answer>]  ← included when generating Q5

Generate a gentle follow-up question about an unresolved concern from the recent
entries above, or signal done.
```

### Error handling for lookback turns

Lookback questions are optional by design. Any error (OpenRouter failure, parse error, empty response, unexpected shape) causes the function to return `{ "done": true }` rather than surfacing an error to the user. The error is logged via ADR-003.

## User State (`user_state`)

`user_state` is a single row per user in the `user_state` table. It holds a living ~200-word third-person profile synthesised from all completed journal sessions.

### Schema

| Column | Type | Description |
|--------|------|-------------|
| `user_id` | uuid | One row per user (unique) |
| `content` | text | The synthesised profile text (~200 words) |
| `word_count` | int | Word count of current `content` |
| `session_count` | int | Number of completed sessions processed |
| `last_session_id` | uuid | FK to the most recent contributing session |
| `last_updated_at` | timestamptz | When `content` was last updated by AI |

### When it is updated

After every completed journal session, `journal-save-session` fires a **fire-and-forget** call to `updateUserState()`. This happens after the HTTP response has already been returned to the client — it never blocks the session save.

If the update fails for any reason (OpenRouter error, DB write error), the session is still correctly marked `completed`. The failure is logged under `phase: "journal_state_update"`.

### Update prompt (incremental merge)

The profile is never fully rebuilt from scratch — only the new session's Q&A is merged into the existing profile:

**System prompt:**
```
You are maintaining a private, evolving user profile for the Sanctuary journaling app.
Your task is to write a fully synthesised, coherent profile that integrates what was
already known about the user with insights from their latest journal session.

This is a COMPLETE REWRITE — do not copy the prior profile verbatim or append new
observations to the end of it. Read both the prior profile and the new session, then
produce a single unified profile that feels like one coherent document.

Rules:
- Write in third person (e.g. "The user..." or "They...")
- Target length: ~250 words (200–300 acceptable)
- Synthesise across: recurring themes, current struggles and challenges, recent events
  mentioned, emotional patterns, relationships or people mentioned, goals or intentions
  expressed
- NEVER infer or assume things not explicitly mentioned by the user
- Naturally weave in important context from the prior profile — do not list old facts
  then new facts; integrate them
- Replace or update observations that the new session contradicts or evolves
- Write observations that will remain meaningful weeks later — avoid ephemeral
  references like "today" or "this week"
- Output ONLY the profile text — no preamble, no headings, no meta-commentary

Prior profile (may be empty):
<user_state.content or placeholder>
```

**User message:**
```
New journal session Q&A:

Q1: <question>
A1: <answer>
...

Write the updated profile.
```

### How `user_state` feeds into journal questions

`user_state.content` is included in the system prompt for Q2 and Q3 as "User's current context". The AI uses it silently as background — it must never quote it back directly or reference facts the user has not brought up in the current session.

For Q1, `user_state` is not loaded. Q1 is returned instantly with no DB reads.

For Q4/Q5 (lookback), `user_state` is not used — those questions draw only from recent `journal_entries`.

## Model Resolution

All LLM calls in the journal subsystem use the same model resolution chain:

```
OPENROUTER_JOURNAL_MODEL → OPENROUTER_TOPIC_MODEL → google/gemini-2.0-flash-001
```

Set `OPENROUTER_JOURNAL_MODEL` in Supabase secrets to pin a different model for journal calls without affecting other features.

## Privacy and Logging (ADR-003)

Journal calls are logged under `phase: "journal_question"` (Q2-Q5) and `phase: "journal_state_update"` (state merge). The following rules apply:

| What | Logged? |
|------|---------|
| Raw question text | No — only `content_preview` (truncated to 200 chars) |
| Raw answer text | **Never** — only `answer_char_count` per turn |
| `user_state.content` | **Never** — only `prior_state_char_count` and `updated_state_char_count` |
| OCEAN scores | **Never** |
| Session ID | Yes |
| Turn index | Yes |
| Latency (ms) | Yes |
| OpenRouter HTTP status | Yes (on error) |

`user_state` is never shown to the user during an active journal session, to avoid biasing their responses. It is readable via the "Your profile" screen in Settings after the session is complete.
